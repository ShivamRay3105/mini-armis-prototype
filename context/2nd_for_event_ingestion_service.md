I am rebuilding a microservices-based OT (Operational Technology) security monitoring platform written in Java using Spring Boot and Kafka. The system architecture consists of multiple services that communicate through REST and event streaming. The services include: an Auth Service that handles authentication using JWT access tokens and refresh tokens (tokens previously issued and transported via cookies through the API Gateway), an API Gateway built with Spring Cloud Gateway that routes requests and validates JWT tokens, a Service Registry using Netflix Eureka for service discovery, an Asset Service that manages industrial device data (PLCs, HMIs, RTUs) with CRUD operations backed by a database, an Event Ingestion Service that receives OT network events through an HTTP endpoint (POST /events), validates the request payload using Spring Validation, verifies the asset through the Asset Service via REST, updates the asset’s lastSeen timestamp, enriches the event with metadata such as timestamp and source, and then publishes the event to Kafka topic “asset-events”. This service is stateless and does not persist events in a database; its responsibility is HTTP → validation → enrichment → Kafka. Kafka is used as the central event backbone of the platform and provides decoupling, asynchronous processing, and failure isolation. The Kafka setup includes brokers that store topics, topics that represent event streams (e.g., asset-events and later risk-events), partitions that allow horizontal scaling and guarantee ordering within a partition, producers that publish events (Event Ingestion Service), and consumers that read events (future services like Risk Engine). Consumers operate in consumer groups where partitions are distributed across consumers for scalability. Each message has an offset representing its position in a partition, and consumers commit offsets after successful processing so they can resume from the correct position. Kafka also supports retention policies (e.g., messages kept for several days) and replication across brokers for fault tolerance. Ordering is guaranteed only within a single partition, not across partitions. In the next stage of the system, a Risk Engine service will consume events from the asset-events topic, optionally enrich them with asset metadata from the Asset Service using a REST client (preferably Spring RestClient rather than Feign to keep the dependency surface minimal and the behavior explicit), apply deterministic rule-based risk calculations (for example protocol violations, authentication failures, or critical zone activity), and then publish results to another Kafka topic such as risk-events which will later be consumed by an Alert Service to generate alerts or notifications. The system follows an event-driven architecture where services are loosely coupled and communicate primarily through Kafka instead of synchronous REST chains. This enables asynchronous processing, resilience to service failures, and independent scaling of services. Key architectural concepts relevant to this system include event versioning (adding a version field to event schemas so older consumers remain compatible when schemas evolve) and idempotent processing (ensuring that processing the same event multiple times produces the same result because Kafka can deliver messages more than once). The technology stack includes Java 21, Spring Boot, Spring Web for REST endpoints, Spring for Apache Kafka for producers and consumers, Jakarta Bean Validation for request validation, Lombok for reducing boilerplate (e.g., @Slf4j, @RequiredArgsConstructor, @Data, @Builder), SLF4J with Logback for logging, and constructor-based dependency injection instead of field injection. The coding architecture generally follows Controller → Service → Repository layering where appropriate (e.g., Asset Service), while event-driven services like Event Ingestion and Risk Engine focus more on producers, consumers, and processing services rather than database repositories.
